# Synthetic Demo Corpus

Everything in this directory is **100% synthetic and fictional**. There is
no real facility, company, or person behind any of it, no real
equipment vendor is named (Aurora Power Systems, Meridian Industrial Park,
etc. are invented for this demo), and none of the documents are derived
from any real source material. It exists purely to give `open-kb` a
runnable, self-contained example corpus for `examples/demo.sh` and the
test suite.

The fictional setting is a generic industrial facility ("Meridian
Industrial Park, Building 4 plant room") with a small, consistent set of
equipment tags used across multiple documents, so the entity/registry and
retrieval pipelines have real cross-document signal to work with:

| Tag | Equipment |
|---|---|
| `DG1` | Standby diesel generator 1 |
| `DG2` | Standby diesel generator 2 |
| `MSB-1` | Main low-voltage switchboard |
| `FP-101` | Electric fire pump |
| `CWP-01` | Chilled water circulation pump |
| `AHU-3` | Air handling unit |

## Files and what each demonstrates

- **`dg1-diesel-generator-manual.md`** / **`dg2-diesel-generator-manual.md`**
  — a pair of near-identical sister-unit manuals (same rating, mostly
  shared part numbers, one unit-specific wear item each). Both
  cross-reference `MSB-1` for their electrical interconnection and
  `FP-101`/`AHU-3` as downstream loads, and each other by tag. Exercises
  chunking, entity extraction (tags + make/model where present), and the
  `_different_unit` merge-guard in `entities/merge.py` (a real pair of
  registry rows, `DG1` vs `DG2`, that share heavy document co-occurrence
  but must never be proposed as a merge).

- **`msb1-switchboard-manual.md`** — the hub document: references `DG1`,
  `DG2`, `FP-101`, and `AHU-3` as sources/feeders. Provides the strongest
  cross-document co-occurrence signal in the corpus.

- **`fp101-fire-pump-manual.md`** — cross-references `CWP-01` via a
  load-shed interlock and `MSB-1` for supply. Together with
  `cwp01-chilled-water-pump-manual.md` this exercises a second
  independent co-occurrence pair distinct from the DG1/DG2 pair.

- **`cwp01-chilled-water-pump-manual.md`** — cross-references `FP-101`
  (the same interlock, from the other side) and `AHU-3` (its cooling
  load).

- **`ahu3-air-handling-unit-manual.md`** — cross-references `CWP-01`
  (chilled water source) and `MSB-1` (electrical supply and standby
  changeover behaviour).

- **`dg1-commissioning-report.md`** — describes the *same physical unit*
  as `dg1-diesel-generator-manual.md`, but exclusively by manufacturer
  make/model ("Aurora Power Systems APG-500") rather than by facility tag,
  and explicitly narrates enough shared context (Building 4 plant room,
  odd-week duty cycle, feeding the main switchboard, sister unit in the
  same room) to plausibly co-occur with the DG1 manual once both are
  entity-extracted. This is the exact scenario `entities/merge.py` phase C
  exists for: two registry rows for one physical item, one tag-only
  (`DG1`) and one make+model-only (`Aurora Power Systems` / `APG-500`),
  that should be proposed as a merge candidate. The test suite seeds this
  scenario's `doc_entities` payloads directly (bypassing the LLM call);
  this document is written so the same scenario is *also* plausible if you
  run `examples/demo.sh` end-to-end against a real local LLM.

- **`fp101-jockey-pump-sop_revA.md`** / **`fp101-jockey-pump-sop_revB.md`**
  — a revision-twin pair with one meaningful content change (the weekly
  check interval is revised from 7 days to 3 days in rev B, with a stated
  reason). Exercises `dedupe.find_revision_families` — same normalised
  stem, same extension, same `rev-letter` revision convention, rev B
  correctly identified as the one to keep.

- **`cable-list.xlsx`** — generated by `../make_corpus.py`. Sheet 1
  ("Cable Register") is a real register: a title row, a header row
  (`Cable Number / From / To / Type / Cores / Route`), and 80 data rows
  referencing the same six tags as `From`/`To` endpoints. Sheet 2 ("Notes
  (ignore)") is deliberately junk — stray notes, no header row with 3+
  non-empty cells matching the header keyword — so
  `ingest.extract.extract_register`'s header-detection logic is genuinely
  exercised against noise rather than a hand-picked clean sheet.

- **`datasheet.pdf`** — generated by `../make_corpus.py`. Two pages of
  real, extractable text (title, a spec table rendered as text, and
  descriptive paragraphs) for the Aurora Power Systems APG-500 — a normal
  PDF text-extraction case, no OCR needed.

- **`graphic-only-drawing.pdf`** — generated by `../make_corpus.py`. A
  single page that is almost entirely vector shapes (rectangles and lines
  standing in for equipment outlines and connections) with only three tiny
  tag labels (`DG1`, `DG2`, `MSB-1`). `page.get_text()` on this page
  returns well under 40 characters, which is the exact "text-thin"
  signal (`OCR_TEXT_THIN_CHARS_PER_PAGE` in `ingest/worker.py`) that makes
  a document a candidate for the vision-describe path in
  `ingest/describe.py` — this file is shaped to exercise that
  classification, not to actually invoke a vision model.

## Regenerating the binary artifacts

`cable-list.xlsx`, `datasheet.pdf`, and `graphic-only-drawing.pdf` are all
generated by `examples/make_corpus.py` and are safe to regenerate at any
time — the script is deterministic and idempotent:

```
.venv/bin/python examples/make_corpus.py
```

The markdown/text manuals in this directory are hand-authored and are not
touched by that script.
